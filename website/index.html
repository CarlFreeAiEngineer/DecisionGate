You're building an application. A user types, "Any chance I could come in next Tuesday?" Your software needs to make one simple decision: is this person asking for an appointment?

Do you really have to get an API key, ship their POTENTIALLY PRIVATE text across the internet to a company they've never heard of, and pay for an API call just to answer that? Or install Ollama, manage a separate runtime, and turn a simple question into an infrastructure project? And then, on top of all that, spend your afternoon begging for JSON?

You're thinking: "I wish I could just load a normal library and call a normal function."

Now you can.

from decisiongate import is_yes

appointment_requested = is_yes(
    "Any chance I could come in next Tuesday?",
    "Is this person asking for an appointment?",
)   # True

That's it. That's the whole product. A function that takes some text and a question, and returns a boolean.

A software component. Not an AI.

Yes, there's a small trained model inside. It's so small and so thoroughly boxed in that you never have to think about it. There is no chat. No prompt. No agent. No "temperature." Nothing to talk to, nothing to coax, nothing to apologize to. You ship it inside your application and you call a function, the same way your grandfather used software components: a library, some arguments, a return value. The kind of thing people did in the 1990s, before every boolean needed a subscription.

No Ollama. No llama.cpp. No TensorFlow. No agent harness. No network. No API key. No bill. The whole thing runs on the CPU inside your own process, on the user's own machine. Their text never leaves it.

It's like a regex library

Every language has one. You hand it a pattern and some text, and you get back a boolean. Nobody runs a regex server. Nobody has a regex API key. Nobody thinks of it as AI. You just call it, thousands of times a second, and get on with your day.

DecisionGate is the same kind of thing, except the pattern is a question in plain English:

re.search(r"\b(appointment|come in|book|schedule)\b", text)   # the old way
is_yes(text, "Is this person asking for an appointment?")     # the new way

Reach for it on the day the regex stops working. Which, for human language input, is RIGHT NOW.

The other half of the brain

There is a famous set of experiments on people whose two brain hemispheres were surgically separated. Only one side can talk. The other side is silent, but it isn't stupid: ask it a question and it answers, correctly, by pointing. It just never explains itself. CGP Grey has a lovely video about it.

Large language models are the talking side. Wonderful at explaining, terrible at shutting up. DecisionGate is the silent side: it reads, it decides, it points at yes or no or one of your options, and it says nothing else. Give your code both halves and let each do what it's good at.

If you know JEV from TypeSafe AI, the brain under the hood is similar: a small classifier that takes some text and a question and returns a typed answer with a probability, instead of generating prose. But JEV is a paid API on somebody else's server. DecisionGate is a library file in your build. For a working programmer the two are as different as a web service and a function call: no account, no network, no bill, no one else's outage, and the model is yours to retrain.

It's fast, too. The first call loads the model and takes a moment; after that, a decision takes about 70 milliseconds on a laptop CPU, with no network round trip to wait on. Same weights, same answers, on Apple silicon Macs, Windows, Linux, and in Chromium, Firefox, and WebKit. Want a probability instead of a boolean, so you can hold the uncertain ones for a human? Want to spell out what counts as yes and what counts as no? Want to pick between several options instead of two? All ordinary function arguments.

Regex and keyword matching is what most software actually does today, and it's the right tool until the day someone writes "no rush, but could I come in Tuesday?" Every fuzzy case becomes another pattern, and every new pattern breaks an old one. DecisionGate is for the decisions that were never really regular expressions.

A hosted LLM is the most flexible and the best on hard cases. It is also an API key, a bill, a network dependency, your users' text on someone else's server, and an afternoon of begging for JSON. That is the reason this project exists.

A local LLM through Ollama or llama.cpp removes the network and the bill and replaces them with a runtime to install, model files to manage, a GPU to wish for, and the same begging for JSON. It turns a simple question into an infrastructure project.

Jev is the closest in spirit: a purpose-built decision model that takes text plus a question and returns a typed answer with a probability, not prose. No begging. But it is a hosted API in early access behind a waitlist, at $0.042 per million input tokens and 70 to 500 milliseconds plus network per call. Your users' text leaves your machine every time, and you cannot retrain it.

Needle 3 is a remarkable piece of engineering aimed at a different job: tool calling, structured extraction, and embeddings on phones, wearables, and microcontrollers, in 8 to 29 MB. You can coax a classification out of it by defining one tool per label, but there is no is_yes(text, question), and it ships as a Python package or C library rather than ready-made Java, Node, browser, and Rust interfaces.

A zero-shot NLI model is what DecisionGate is built from, one layer down. Free and open, and a fine choice if you already live in Python with PyTorch installed and want to write the tokenization, prompting, thresholds, calibration, and packaging yourself. DecisionGate is that work, done once, shipped as a component for six languages.

What if it gives a wrong answer?

GREAT!

That means you can add training data, retrain the model yourself, right there in the project, and contribute your training data back so the whole world benefits.

A wrong answer from someone else's API is a dead end: you file a ticket and hope. A wrong answer here is an improvement you can make yourself. Write down the text, the question, and the right answer, add them to the training data, and retrain. The training data is plain text files in the repository, and the training recipe runs on an ordinary laptop. Keep the improved model for yourself, or send your examples back in a pull request and the next release gets better for everyone. No GPU, no machine-learning degree, no permission required.

Open weights. Open training data. Open recipes. Apache 2.0.
